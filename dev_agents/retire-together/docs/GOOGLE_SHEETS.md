# 구글 로그인과 공통 스프레드시트

2026-11-07 로그인 화면 연결: `http://127.0.0.1:5180/`에서 **Google로 로그인**을 눌러 본인 계정을 선택한다. 첫 성공 계정이 고정 오너이며, 실제 최초 로그인과 활성 오너 세션을 확인했다. 로그인 버튼은 팝업으로 진행하고 완료 후 원래 앱의 메인 대시보드가 열린다. 공통 시트 생성·배우자 초대는 후속 작업이다.

갱신: 2026-11-06. 사용자가 먼저 구글 계정으로 시작해 고정 오너가 되고, 초대받은 배우자가 같은 가구와 공통 스프레드시트에 합류한다. 자산 데이터는 두 분의 구글 시트를 원천으로 유지한다. 사진·직접 입력·파일로 등록한 결과도 시트에 쓰이며, 시트에서 직접 고친 값은 앱에 반영한다.

SHARE-02의 웹 OAuth·서버 세션·고정 오너 코드와 합성 자동 테스트를 추가했다(2026-11-07). 최소 로그인 화면·계정 메뉴·프론트 CSRF 연결 및 브라우저 검수를 추가하고 공용 서버를 웹 모드로 전환했다. 실제 최초 Google 로그인과 활성 오너 세션을 확인했다. 기존 `SHEET-01`은 컴퓨터 공용 시트 연결이고, 웹 공통 파일·배우자 초대 화면은 후속 작업이다. 구현 상태의 원본은 [AGENT_DESIGN §0](AGENT_DESIGN.md)의 `SHARE-*` 작업이다.

## 확정한 제품 규칙

- 첫 운영은 사용자 본인 계정이 오너인 한 가구로 시작한다. 오너는 최초 설정 후 고정하고, 앱에 오너 양도·교체 기능을 만들지 않는다.
- 오너는 공통 시트 생성·기존 시트 연결과 배우자 초대를 관리한다. 새 시트는 오너의 Google Drive에 만든다. 기존 시트도 오너 소유인지 확인한 뒤 연결한다.
- 배우자는 오너의 초대를 받아야 합류할 수 있다. 초대 없는 계정은 구글 본인 확인에 성공해도 가구 데이터에 접근할 수 없다. 별도 가구를 자유롭게 만드는 공개 가입은 이번 범위에서 제외한다.
- 초대 수락은 최초 합류 때 한 번만 한다. 이후에는 각자의 구글 계정으로 로그인해 같은 파일을 불러온다.
- 공통 파일은 가구에 연결된 `spreadsheet_id`로 식별한다. 파일 이름이나 로그인 순서로 오너·가구·시트를 다시 정하지 않는다.
- 오너는 앱 관리 역할이다. 배우자 자산의 명의나 기존 투자 결정까지 오너 소유로 바꾸지 않는다.

오너 고정은 사용자 결정에 따른 제품 규칙이다. 구글 자체는 계정 유형 등의 조건에 따라 파일 소유권 이전을 지원한다. 사용자가 Drive에서 파일 소유권을 바꾸더라도 앱 오너는 자동 변경하지 않고 연결 상태를 확인하도록 한다. [Google Drive 소유권 이전](https://developers.google.com/workspace/drive/api/guides/transfer-file)

## 처음 시작하고 다시 들어오는 흐름

1. **오너 시작**: 앱의 최초 설정에서 본인이 `Google로 로그인` → 첫 로그인에 성공한 계정으로 우리 집과 고정 오너를 자동 생성한다. 이메일을 미리 허용 목록에 등록하지 않는다(2026-11-07 사용자 재확인). 최초 생성은 원자적으로 한 번만 성공하며 이후 로그인으로 오너를 바꾸지 않는다. 초기 설정은 운영자만 접근할 수 있게 하고 공개 접속을 열기 전에 본인이 완료한다.
2. **공통 파일 연결**: 이미 연결 기록이 있으면 해당 파일을 확인해 불러온다. 처음 연결하는 기존 파일은 파일 선택창에서 고른다. 사용할 파일이 없을 때 오너가 `새 공통 시트 만들기`를 누른다. 생성 재시도·새로고침으로 파일이 중복 생성되지 않도록 한다.
3. **우리 자료 가져오기**: 기존 로컬 자료의 항목과 건수를 보여 주고 오너가 이전을 선택한다. 기존 시트를 무조건 덮어쓰거나 빈 시트로 간주하지 않는다.
4. **배우자 초대**: 오너가 배우자 이메일을 지정해 초대 링크/코드를 만든다. 1차 전달 방식은 링크 복사로 두고, 이메일 자동 발송은 별도 기능으로 남긴다.
5. **배우자 합류**: 초대 링크 열기 또는 코드 입력 → 자기 구글 계정으로 본인 확인 → 초대 대상 확인 → 같은 가구·같은 시트 연결. 회원 연결과 필요한 시트 접근 확인이 끝난 뒤 입장한다.
6. **다음 로그인**: 기존 멤버십을 찾아 바로 가구로 들어간다. 만료된 구글 연결은 다시 동의받되, 기존 가구·오너·파일 연결 기록을 지우거나 새 가구를 만들지 않는다.

최초에 연결하지 않은 Drive 파일을 이름만으로 자동 선택하지 않는다. 필요한 파일에만 접근하는 `drive.file` 범위와 Google Picker를 우선 검토한다. 이 범위는 Drive 전체를 검색하는 권한이 아니므로, 초대받은 배우자에게도 필요하면 같은 파일을 한 번 선택하도록 안내한다. 공유 권한과 앱의 파일 접근 승인은 각각 확인한다. [Drive 권한 범위](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), [Google Picker](https://developers.google.com/workspace/drive/picker/guides/overview), [Sheets 권한 범위](https://developers.google.com/workspace/sheets/api/scopes)

## 구현 기준

다음은 위 사용자 결정을 구현하기 위한 설계 기준이다. 세부 만료 시간·화면 문구는 구현 때 정한다.

### 로그인과 가구 권한

- 웹 앱용 OAuth 클라이언트와 서버 콜백을 사용한다. 현재 데스크톱용 `InstalledAppFlow`와 컴퓨터 공용 `token.json`을 웹 로그인으로 재사용하지 않는다. OAuth 클라이언트 설정은 앱 운영자가 한 번 수행하며 배우자에게 JSON 입력을 요구하지 않는다.
- 검증한 Google ID 토큰의 `sub`를 계정 식별자로 사용한다. 이메일은 `email_verified`를 확인해 최초 오너 확인·초대 대상 대조에 쓰되 장기 사용자 키로 쓰지 않는다. 토큰 서명·발급자·대상·만료와 흐름의 `state`·`nonce`를 검사한다. [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)
- 서버가 사용자·가구·멤버십과 고정 오너를 관리한다. `household.owner_user_id`는 최초 설정의 첫 검증된 Google 로그인 때만 기록하며, 서버와 저장소 양쪽에서 재설정·승격 요청을 차단한다. 오너 계정 이메일의 사전 지정은 요구하지 않는다.
- 서버 세션과 HTTPS를 사용하고 쿠키에 HttpOnly·Secure·적절한 SameSite를 적용한다. 상태 변경 API에는 CSRF 방어를 둔다. 개인 데이터 API·파일 내려받기·등록/설정 API 모두에서 세션과 가구 권한을 확인한다.
- 구글 토큰은 계정별로 분리해 서버에서 보호하고 시트·브라우저 장기 저장소·로그에 넣지 않는다. 로그아웃과 시트 연결 해제를 구분한다. [웹 서버 OAuth 흐름](https://developers.google.com/identity/protocols/oauth2/web-server)

### 초대와 시트 공유

- 초대에는 가구·초대한 오너·대상 이메일·만료 시각·수락/취소 상태를 연결한다. 추측하기 어려운 코드의 해시를 저장하고, 발급/검증 횟수를 제한한다. 일회용 수락은 원자적으로 처리한다.
- 다른 계정·만료·취소·사용된 초대는 거부한다. 동시에 수락하거나 재시도해도 배우자 멤버십이 중복되지 않아야 한다. 최초 범위는 오너 1명과 배우자 1명이다.
- 앱 멤버십과 구글 시트 공유 권한을 별도로 확인한다. 초대 수락 후 같은 파일에 필요한 공유를 적용하되, 구글 공유만 성공한 상태를 앱 가입 완료로 표시하지 않는다. 중간 실패는 진행 상태를 남겨 같은 초대를 재개하거나 권한을 정리한다. [Drive 공유 권한](https://developers.google.com/workspace/drive/api/guides/manage-sharing)
- 시트 편집자라면 시트 전체 자료를 직접 볼 수 있으므로 앱의 개인별 편집 제한이 시트의 행 단위 보안을 보장한다고 설명하지 않는다. 상대 자산의 앱 내 편집 범위는 기존 가족 계정 원칙에 따라 별도 설정으로 명시한다.
- 초대 취소와 가입 후 접근 해제는 구분한다. 가입 후 해제 시 서버 세션·멤버십을 차단하고 앱이 부여한 Drive 공유 권한도 확인·정리한다. 오너 자동 승계는 하지 않는다. 다른 경로로 남은 Drive 접근 권한이 있으면 그대로 설명한다.

### 공유 데이터와 기존 자료 이전

| 데이터 | 현재 저장 | 공유 사용을 위한 작업 |
|---|---|---|

| 내 정보·배우자 정보 | 로컬 SQLite `family` | 같은 가구에서 읽는 원천과 스키마 지정, 계정과 사람을 연결 |
| 은퇴 계획·생활비·수령 가정 | 로컬 SQLite `retirement_plan` | 공통 시트의 계획 탭으로 확장하는 안을 기준으로 스키마·이전 작성 |
| 부동산 후보·계획·추적 기록 | 로컬 SQLite `property_move`·`property_track` | 공유 대상 필드와 이력의 저장·복원 방식 정의 |
| 계좌·전략 선택·결정 이력 | 로컬 YAML·CSV·DB 등 | 사용자별 자료와 공통 투자 규칙을 구분해 이전 목록 작성 |
| 계정·세션·초대·가구와 파일 연결·구글 토큰 | 웹 인증 저장소 없음 | 서버 저장소에 신설; 공통 시트에 인증 정보 저장 금지 |

- 계획과 프로필을 어떤 탭으로 옮길지는 `SHARE-05`에서 확정한다. 두 기기에서 같은 가구 정보를 읽어야 하며, 캐시를 원천 데이터와 혼동하지 않는다.
- 사람은 고정 `member_id`로 식별한다. 현재 `me/partner/joint` 자료는 최초 오너 기준 사람과 대응시켜 이전하고, 화면의 ‘나/배우자’만 로그인한 사람 기준으로 바꾼다. 공동 자산·연금 수령자·은퇴 기준 사람이 뒤집히지 않도록 한다.
- 이전 전 로컬 원본과 기존 시트를 백업하고 건수·합계·명의를 대조한다. 기존 시트가 있으면 덮어쓰기 전에 충돌을 보여 준다. 같은 이전을 반복해도 자료를 중복 등록하지 않는다.
- 앱의 쓰기는 가구 단위로 직렬화하고 변경 버전을 확인한다. 시트 직접 편집과의 동시 저장은 별도 충돌·복구 설계가 필요하다. 현재 탭 전체 지우기→다시 쓰기 구현을 부부 동시 사용에 그대로 적용하지 않는다.
- 시트 삭제·권한 철회·토큰 만료·네트워크 오류를 ‘파일 없음’으로 뭉쳐 새 파일을 만들지 않는다. 마지막 연결은 유지하고 오류와 재연결 경로를 보여 준다. 공유 모드에서 개인 로컬 장부로 조용히 전환하지 않는다.

## 구현 순서와 완료 기준

작업별 담당·상태는 `AGENT_DESIGN.md` §0에서만 관리한다. 순서는 `SHARE-02` 고정 오너·세션 → `SHARE-03` 공통 파일 → `SHARE-04` 초대·공유 → `SHARE-05` 데이터 이전 → `SHARE-06` 첫 화면 → `SHARE-07` 두 계정 실검증이다. `SHARE-05`의 데이터 조사는 로그인 구현과 함께 시작한다.

완료하려면 오너 첫 설정·재로그인, 배우자 초대 수락·재로그인, 초대 없는 제3자 차단, 같은 파일 복원, 두 기기의 명의·계획 일치가 모두 확인되어야 한다. 오너 변경 거부, 초대 만료/재사용/동시 수락, 중복 시트 생성 방지, 권한 해제, 저장 충돌·이전 복구도 검증한다. 자동 테스트는 임시 DB·합성 자료·가짜 구글 응답을 쓰고 실제 두 계정 검증은 별도 테스트 시트에서 수행한다.

운영용 자격 증명은 실제 Google 접속 검증 단계에 필요하다. 설정값이 없어도 인증 코드·설정 유효성 검사·가짜 Google 응답/임시 DB 테스트를 먼저 구현한다. 실제 로그인 미검증을 구현 전체의 착수 불가로 처리하지 않는다.

## 웹 로그인 앱 등록 — 운영자가 한 번

일반 사용자나 배우자는 OAuth 클라이언트를 만들지 않는다. 앱 운영자가 한 번 등록하고, 사용자는 앱에서 Google 계정을 선택해 로그인한다. 최초 설정의 첫 사용자가 고정 오너이며 이후 가입은 초대가 필요하다.

1. [Google Cloud Console](https://console.cloud.google.com/)에서 프로젝트 이름은 영문 `Retire Together`로 생성/선택한다. 프로젝트 ID는 콘솔의 자동 생성값을 사용한다. [프로젝트 이름·ID 규칙](https://docs.cloud.google.com/resource-manager/docs/creating-managing-projects)
2. **Google Auth Platform → Branding → 시작하기**에서 앱 이름 `둘이서은퇴`, 지원/연락 이메일을 입력하고 대상은 **외부(External)**로 설정한다.
3. **Audience → Test users**에 본인 Google 이메일을 추가한다. 배우자 테스트 전에 배우자도 추가하며 개발 중에는 테스트 상태를 유지한다. [공식 동의 화면 설정](https://developers.google.com/workspace/guides/configure-oauth-consent)
4. **Clients → Create client → Web application**을 선택한다. 이름은 `둘이서은퇴 로컬 개발`. 승인된 JavaScript 원본은 `http://127.0.0.1:5180`, 승인된 리디렉션 URI는 `http://127.0.0.1:5180/api/auth/google/callback`로 등록한다. 콜백 코드는 SHARE-02에 추가했으며 실제 Google 왕복은 아직 검증 전이다. 배포 시에는 실제 HTTPS 주소를 별도로 등록한다. [공식 웹 OAuth 안내](https://developers.google.com/identity/protocols/oauth2/web-server)
5. 생성 직후 클라이언트 JSON을 다운로드해 로컬에 보관한다. 클라이언트 비밀값을 대화·문서·Git에 붙여 넣지 않는다. 구현 시 서버 전용 설정으로 연결하며 브라우저 코드에 포함하지 않는다.

현재 PC 설정 전달(2026-11-07): 사용자가 제공한 웹 OAuth JSON은 `data/local/google/web-client.json`에 보관한다(Git 제외, 파일 권한 0600). 위 개발 원본/콜백을 등록한 웹 클라이언트임을 확인했다. SHARE-02 구현에서 서버 전용으로 이 경로를 읽으며, 기존 데스크톱용 `client_secret.json`과 구분한다. 실제 Google 동의 화면의 테스트 사용자 설정과 사용자 로그인 성공 여부는 별도 확인해야 한다.

SHARE-02 서버 설정·검수 순서는 [LOCAL_DEVELOPMENT의 웹 인증 절](LOCAL_DEVELOPMENT.md#share-02-웹-인증-설정과-검수)을 따른다. 아래는 현재 로컬 시트 연결의 기존 안내이며, 새 웹 로그인에는 위 **웹 애플리케이션** 유형을 사용한다.

## 기존 로컬 연결 설정

앱이 구글 시트를 읽고 쓰려면 구글이 발급하는 "OAuth 클라이언트"가 필요하다. 이건 구글 계정 주인만 만들 수 있다. 비용은 없다.

1. https://console.cloud.google.com 에 시트를 둘 구글 계정으로 로그인한다.
2. 위쪽 프로젝트 선택 → **새 프로젝트** → 이름 `둘이서은퇴` → 만들기.
3. 왼쪽 메뉴 **API 및 서비스 → 라이브러리** → `Google Sheets API` 검색 → **사용**.
4. **API 및 서비스 → OAuth 동의 화면** → 사용자 유형 **외부** → 앱 이름 `둘이서은퇴`, 지원 이메일은 본인 → 저장. 범위는 비워 두고 다음 → **테스트 사용자**에 두 분의 Gmail 주소를 추가 → 저장. (게시하지 않고 "테스트" 상태로 두면 된다. 테스트 사용자만 로그인할 수 있다.)
5. **API 및 서비스 → 사용자 인증 정보 → 사용자 인증 정보 만들기 → OAuth 클라이언트 ID** → 애플리케이션 유형 **데스크톱 앱** → 이름 아무거나 → 만들기 → **JSON 다운로드**.
6. 앱을 열고 머리글의 **로컬 저장** 배지(또는 설정)를 눌러 "구글 시트 연결" 창을 연다.
   1. 1단계: 내려받은 JSON 파일 내용을 그대로 붙여 넣고 **열쇠 저장**.
   2. 2단계: **구글로 연결하기** → 브라우저에 구글 로그인 창이 열린다. 4단계에서 넣은 계정으로 로그인하고 "확인되지 않은 앱" 경고가 나오면 **계속** → 시트 권한 **허용**. 창에 "연결됐어요"가 보이면 닫는다.
   3. 3단계: **새 시트 만들기**(권장) 또는 이미 쓰는 시트 주소를 붙여 넣고 **이 시트 쓰기**.
7. 머리글 배지가 **구글 시트**로 바뀌면 끝. 로컬에 등록해 둔 자산이 있으면 비어 있는 시트로 자동으로 옮겨진다.

배우자 컴퓨터에서도 같은 시트를 쓰려면: 같은 JSON을 붙여 넣고(한 프로젝트를 같이 씀), 2단계에서 배우자 계정으로 로그인하고, 3단계에서 같은 시트 주소를 붙여 넣는다. 시트는 구글 드라이브에서 배우자에게 **편집자**로 공유해 둔다.

## 시트 모양

시트 `둘이서은퇴`에 탭 두 개. 1행은 머리글이며 앱이 읽을 때 이름을 확인한다 — 열 이름을 바꾸거나 순서를 바꾸면 "머리글이 앱 양식과 달라요"가 뜬다. 열은 끝에만 추가한다.

| 탭 | 열 | 뜻 |
|---|---|---|
| `자산` | id, owner, pocket, assetClass, name, account, account_id, amount, as_of, source, version, updated_at, request_id, parent_id, valuation_source, share_percent | '우리 자산' 표의 한 줄. owner는 me/partner/joint, pocket은 retirement/cash/property/debt, assetClass는 stock/long_bond/mid_bond/gold/commodity/cash/property/mixed/debt, amount는 원 단위 정수, as_of는 `2026-10-27` 문자열. source는 manual(직접 입력)/capture(사진)/file(파일). version은 앱이 올린다 — 시트에서 고칠 때는 그대로 두면 된다 |
| `보유종목` | account_id, ticker_name, ticker, qty, price, as_of, updated_at | 사진·파일로 등록한 계좌의 종목 단위 잔고. 리밸런싱 엔진이 쓰는 모양과 같다(`tools/parse_balance.HOLDING_COLUMNS`) |

시트에서 직접 할 수 있는 것: 금액·이름·기준일 고치기, 줄 지우기, 직접 입력 자산 줄 추가(id는 아무 고유 문자열, version 1). 앱은 몇 초 안에 반영한다(읽기 캐시 5초).
하면 안 되는 것: 1행 머리글 바꾸기, 탭 이름 바꾸기, 같은 id를 두 줄에 쓰기.

## 앱 쪽 구조

- `tools/sheets.py`: 시트 API 클라이언트(읽기·쓰기·탭 보장), OAuth 토큰 저장/갱신(`data/local/google/`), 시트 만들기/지정. 테스트용 `MemorySheets`.
- `backend/ledger.py`: 시트가 연결돼 있으면 `SheetStore`(시트가 원천), 아니면 None → `backend/storage.py`가 SQLite를 쓴다. 저장 규칙(버전 충돌·세부 자산·중복 계좌)은 두 저장소가 같다.
- `backend/google_api.py`: `/api/google/status · client-secret · connect · spreadsheet · connection`.
- `backend/registration.py`: `/api/register/accounts · capture · file · commit` — 사진·파일 등록(REG-01). 저장 때 `data/snapshots`(엔진용)와 시트 `보유종목` 탭에 함께 쓴다.
- 내 정보·배우자 정보(프로필)는 시트가 아니라 로컬 SQLite에 둔다(Claude 가정, DECISIONS 참조).
- 테스트·브라우저 테스트는 `RETIRE_SHEETS=off`로 시트를 절대 열지 않는다.

## 안 될 때

- "권한이 없어요": 로그인한 계정으로 그 시트를 열 수 있는지(공유) 확인. 연결 끊고 다시 연결.
- "확인되지 않은 앱": 4단계 테스트 사용자에 그 계정이 있는지 확인. 경고 화면에서 **고급 → 둘이서은퇴(안전하지 않음)으로 이동**을 눌러도 된다(본인이 만든 앱이다).
- 토큰이 만료되면 앱이 자동 갱신한다. 테스트 앱의 refresh token은 구글 정책상 7일마다 만료될 수 있다 — 그러면 2단계를 다시 한다. 동의 화면을 "프로덕션"으로 게시하면(검토 없이 가능, 경고만 뜸) 7일 제한이 없어진다.
